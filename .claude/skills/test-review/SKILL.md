# Регламент тестирования и независимого ревью

> **Единый источник правды (single source of truth).** Все антипаттерны, принципы, выбор слоя, TDD-цикл и правило Playwright-for-UI определены здесь. `sdd-reviewer`, `sdd-qa`, `spec-implement`, `spec-review`, steering docs и CLAUDE.md **ссылаются** на этот файл и не дублируют определения. Меняется регламент — меняется только этот файл.

> Стек-агностичен. Конкретные команды/инструменты — из `tech.md` целевого проекта.

---

## 0. TL;DR для агента

1. **Тест — раньше кода. Всегда.** Никаких исключений на «маленькие правки».
2. **RED наблюдается, не объявляется.** Тест реально запускается и реально падает по причине AC — вывод падения захватывается.
3. **Тест проверяет поведение, не реализацию.** Рефакторинг внутрянки не должен ломать тест.
4. **Один тест на пару RED/GREEN.** Между red и green меняется только результат прогона, не сам тест.
5. **Тест и код, который его зеленит, — в разных коммитах.**
6. **Независимый ревьюер ≠ автор.** Один агент не пишет тест, код и сам себя проверяет.
7. **Слой теста — по контракту, который он защищает** (§3).
8. **Любой UI → headless-e2e (web: Playwright) обязателен. Всегда.** (§6)
9. **Coverage — индикатор, не цель.**

## 1. Фундаментальные принципы (P1–P6)

### P1. Test-first, всегда
Задача начинается с теста, который **падает по ожидаемой причине** — не «символ не определён», а «для конкретного входа результат не тот».
```
RED      → тест реально прогнан и упал с ожидаемым сообщением
GREEN    → минимальный код, чтобы тест прошёл (тот же тест, inner-loop прогонов)
REFACTOR → чистка без изменения поведения, тест остаётся зелёным
```

### P2. Поведение > реализация
Тест переживает любой рефакторинг внутрянки. Если переименование приватного метода ломает тест — тест написан неправильно.

| Тестировать | НЕ тестировать |
|-------------|----------------|
| Результат запроса / ответ API (response shape) | Имена внутренних функций |
| Состояние хранилища после операции | Структуру вызовов внутри |
| Поведение UI с точки зрения пользователя | Конкретный CSS-класс / приватные поля |

### P3. Тест ради поведения, не ради покрытия
Триггер теста — новое требование/AC, не появление нового метода. 100% coverage на self-affirming тестах — мусор.

### P4. Разделение ролей в петле «человек + AI»
Acceptance criteria и приёмочные тесты — за человеком (или человек правит AI-черновик). Нижние тесты (integration/unit) и код — AI под ревью. **Запрет:** один и тот же агент не может в одной итерации править и тест, и код, который этот тест зеленит — это рождает self-affirming тесты (A1/A7). Отсюда требование **независимого ревьюера** (§5).

### P5. Контрольные точки в git
Перед агентским вмешательством — commit (иначе rollback невозможен). Один коммит не смешивает тестовые и production-файлы (A6).

### P6. Изоляция тестового окружения
Тесты против тестовых контуров (testcontainers / test DC / fake-сервисы), не против production. Агенту запрещён доступ к production-credentials. Эфемерные артефакты зачищаются (A8).

## 2. TDD-цикл RED → GREEN → REFACTOR (с обязательным прогоном)

**RED — тест ДО кода, прогнать красным:**
1. Написать тест из строки тест-плана для AC.
2. **Прогнать реальной командой.** Тест обязан упасть; захватить дословный вывод (assertion mismatch / `locator not found` / timeout / 404).
3. Убедиться: падение по причине AC, **не** compile-error и не «символ не определён». Для статически-типизированных стеков перед прогоном должен быть stub (`panic("not implemented")` / zero-value), иначе red невалиден.
4. **Зелёный до кода → STOP:** тест ничего не проверяет (A1). Переписать тест, не код. *Тест, не упавший красным, не доказывает ничего.*

**GREEN — минимальный код, inner-loop:**
Тот же тест, неизменен. Меняется только результат прогона. Писать минимум → прогонять тот же тест после каждой правки → вывод смещается от RED-сообщения к зелёному. Когда зелёный — прогнать весь релевантный набор (нет регрессий).

**REFACTOR — чистка под зелёным (опционально):**
Чистить дублирование/имена без изменения поведения. После каждой правки прогон — остаётся зелёным; покраснел → поведение изменилось, откат. Отдельный коммит, без правки теста.

> Разбивка на коммиты `test: red` / `feat: green` / `refactor:` и процедура двойного ревью — в `spec-implement`. Этот раздел — нормативный «что и почему», там — «как именно вызывать».

## 3. Иерархия тестов — Testing Trophy

```
E2E              ← мало, дорого, критические пользовательские пути
Integration      ← основная масса
Unit             ← только чистая логика без I/O
Static Analysis  ← бесплатно, обязательно (lint/typecheck/vet)
```

**Слой выбирается по контракту, который тест защищает:**

| Контракт | Слой | Инструмент (пример, уточнять по tech.md) |
|----------|------|------------------------------------------|
| HTTP-эндпоинт, состояние хранилища | Integration (реальная БД) | testcontainers / httptest / pytest |
| Чистая функция (расчёт, парсер, маппинг) | Unit | стандартный test-framework, property-based |
| Пользовательский поток через UI | E2E | **Playwright (web)** / XCUITest / Espresso |
| IaC-ресурс | policy / plan-check | conftest / terraform test |
| Контракт данных / схема | contract-test | schema assertions |

**Запрет:** unit-тест с моком репозитория, повторяющий SQL «в коде» — double-bookkeeping, регрессий миграций не ловит (A2).

## 4. Антипаттерны — A1–A9 + no-red-run (канонический список)

Ревьюер помечает находку по коду. Severity — в §7.

- **A1 — Self-affirming тест:** assert функции против самой себя (`expected := f(x); require.Equal(expected, f(x))`), либо тест зелёный до написания кода. **Ловится прогоном RED.**
- **A2 — Mock-heavy unit вместо integration:** мок БД/очереди/API там, где интеграция с реальным субсистемой была правильным выбором — проверяет, что мок работает, а не код.
- **A3 — Тест приватной реализации:** пинит внутреннюю структуру/имена вместо наблюдаемого поведения; ломается на рефакторинге.
- **A4 — Coverage как KPI:** покрытие обсуждается как цель. Индикатор, не цель.
- **A5 — Тесты-комментарии:** имена `test 1` / `it works`. Имя теста = строка контракта (`returns_409_when_lead_exists`).
- **A6 — Один коммит «test + impl»:** diff смешивает `*_test.*` (или `*.spec.ts` / `*_test.py` / `*.tftest.hcl`) с production-файлами. Исключения: маркер `[gen]` (codegen/фикстуры) или `[stub]` (not-implemented stub рядом с RED-тестом в новом файле).
- **A7 — Правка теста ради зелёного:** тест изменён, чтобы пройти, вместо исправления кода. Диагностика причины — до правки. Правка теста допустима только если изменилась спецификация (с отметкой) или тест проверял реализацию (переписывается на поведение **новым** red-коммитом). «Удалить assertion, чтобы прошло» — запрещено.
- **A8 — Leaked / destructive cleanup:** тест оставляет эфемерные артефакты в живой среде (pod без `--rm`, debug-pod, тестовый ConfigMap/Secret/S3-объект/запись БД/DNS/port-forward/namespace без зачистки) — ИЛИ команда зачистки слишком широкая и задевает production (`kubectl delete --all`, `delete -l app=` без `purpose=smoke-spec-NNN`, `aws s3 rm --recursive` без префикса, `rm -rf /tmp/*`, `DROP/TRUNCATE/DELETE` без `id LIKE 'test-spec-NNN-%'`). Cleanup — часть теста. Операционные детали — в `sdd-conventions` § Cleanup rule / Safety guards.
- **A9 — Hardcoded secret / config в diff.** Триггеры: `(password|secret|token|api[_-]?key|client[_-]?secret)\s*=\s*["'][^"'\s]{8,}["']` (не-placeholder); `postgres(ql)?://[^:]+:[^@]+@` (DSN с inline creds); `AKIA[0-9A-Z]{16}`; `eyJ[A-Za-z0-9_-]{20,}` (JWT); `BEGIN (RSA |EC |OPENSSH )?PRIVATE KEY`; `*.pem`/`*.key`/`*.p12`/`kubeconfig*` без `# test-only`. Исключения: docs/steering с public-endpoints, `*_test.*` с явным `# test-only` маркером, public image tags. При CRITICAL — в `blocking_issues` явный запрос ротации.
- **no-red-run — RED не прогнан / не упал:** красный задекларирован, но реального вывода падения нет (или тест прошёл зелёным на RED-шаге). Тест, который ни разу не упал, ничего не доказывает. **CRITICAL.**

## 5. Независимый ревьюер — adversarial mindset

**Роль:** ревьюер — НЕ автор теста/кода. Его задача — **сломать** тест, а не подтвердить. Это структурно закрывает A1/A7 (см. P4). Inline-review (один агент пишет и сам проверяет) запрещён.

Для каждого теста — 5 вопросов:
1. **По захваченному выводу RED-прогона:** тест падает по причине AC (assertion/поведение), или просто «символ не определён» (compile-error), или — хуже — прошёл зелёным? Валидный red — только assertion-уровень, привязанный к AC.
2. Если удалить ключевую строку `assert`/`require`/`expect` — тест всё ещё ловит реальный баг?
3. Переживёт ли тест переименование внутренней функции / рефакторинг? Или пинит приватную реализацию (A3)?
4. Покрыты ли граничные случаи из requirements (Edge-фаза тест-плана)?
5. Может ли production-код «обмануть» тест (хардкод-return, no-op stub) и пройти?

Любой ответ, вскрывающий слабость, → находка.

**Измерения качества кода (помимо тестов):** баги/логика (nil/null, races, проглоченные ошибки, off-by-one — адаптировать под стек: для IaC — дрейф state, для data pipeline — потеря записей, для frontend — race загрузки); безопасность (инъекции, missing auth/RBAC, tenant isolation, sensitive data в логах); соответствие steering (слои по `structure.md`, стандарты `tech.md`); качество (naming, dead code, правильные коды ответа/статусы).

## 6. UI — Playwright обязателен ВСЕГДА

**Любая** новая или изменённая фронтенд-фича (страница, форма, навигация, интерактивный компонент, видимое изменение поведения UI) **обязана** иметь headless-e2e-сценарий и пройти полный RED → GREEN:

- Web → **Playwright** (`*.spec.ts`). Mobile → XCUITest/Espresso. Без исключений на «мелкую правку».
- **RED реален:** тест пишется ДО UI-кода и реально падает — браузер физически не находит ещё не существующий элемент (`locator not found` / timeout). Зелёный с первого прогона = пустышка (A1).
- **Покрытием считается ТОЛЬКО assertion на наблюдаемом DOM-состоянии:** `expect(locator).toBeVisible()`, текст, переход, состояние после действия.
- **НЕ считаются покрытием UI:** `curl … → 200`, проверка только console-errors, `mount`/`mountSuspended` без поведенческого assertion, скриншот без проверки.
- UI-фича без зелёного e2e-теста **не мерджится** (CRITICAL).

## 7. Severity и вердикт

- **CRITICAL** (блокирует merge): нарушение steering, сломанные тесты, security, A1/A3/A7/A8/A9, **no-red-run**, UI-фича без зелёного Playwright-e2e.
- **HIGH** (требует внимания автора): отсутствует тест для AC, неполные acceptance criteria, A2/A6.
- **LOW** (рекомендация): стиль, naming, A4/A5.

Формат вердикта (используется sdd-reviewer):
```yaml
verdict: PASS | PASS_WITH_NOTES | FAIL
blocking_issues:
  - rule: A3 | no-red-run | steering:structure.md#layers | ...
    location: path/to/file.ext:LN
    why: одно предложение — нарушение и почему блокирует
notes:
  - low-severity наблюдения (не блокируют)
```
Все проходы PASS, нет CRITICAL/HIGH → `PASS`. Только LOW → `PASS_WITH_NOTES`. Любой CRITICAL/HIGH → `FAIL` с непустым `blocking_issues`.
