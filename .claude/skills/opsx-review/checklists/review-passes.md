# Review Passes — OpenSpec change

Семь проходов SDD-ревью, переведённые на артефакты OpenSpec. Источник требований —
не `requirements.md`, а **delta-спеки** `openspec/changes/<name>/specs/<capability>/spec.md`:
каждый `#### Scenario:` (Given / When / Then) — отдельный acceptance criterion.

## Pass A: Соответствие delta-спекам
- Каждый `#### Scenario:` из каждой delta-спеки — реализован? Указать `file:line`.
- `ADDED` / `MODIFIED` / `REMOVED` requirements отражены в коде именно так, как размечены:
  `REMOVED` — поведение действительно удалено, а не оставлено «на всякий случай».
- Формулировки SHALL / MUST выполнены буквально, а не «в целом».
- Решения из `design.md` (сигнатуры, контракты, DDL, выбранный механизм) совпадают с кодом.
- Нет изменений сверх границ change — сверить с разделом **Non-goals** в `proposal.md`
  (scope creep в OpenSpec особенно вреден: он не попадёт в delta-спеку и потеряется при archive).

## Pass B: Архитектура и канон проекта
- Слои и направление зависимостей — по `structure.md` (гибрид) или по канону `AGENTS.md`.
- Соблюдены `rules.design` из `openspec/config.yaml` — каждое правило проверить поимённо.
- Конвертация DTO ↔ domain на границе слоёв явная; domain без зависимостей от фреймворка.
- Frontend: импорты через публичный API (index.ts / barrel).
- Новый обход/workaround дописан в проектный список известных граблей, если канон это требует.

## Pass C: Качество кода
- Проект собирается / валидируется — командой из `rules.tasks` («Gate before archive: …»).
- Линтер чист.
- Нет TODO / FIXME / HACK / XXX в новом коде.
- Нет закомментированного кода.
- Нет захардкоженных секретов, URL, портов (кроме тестов).

## Pass D: Тесты и TDD-дисциплина
Канон — skill `test-review` (§1 принципы, §4 антипаттерны A1–A9 + `no-red-run`, §3 выбор слоя).
- Каждый сценарий delta-спеки покрыт тестом на слое своего контракта.
- RED был **наблюдён**, а не объявлен: тест реально прогонялся и падал по причине сценария.
  Отсутствие подтверждения красного прогона — `no-red-run`, CRITICAL.
- Тест и зеленящий его код — в разных коммитах; между RED и GREEN тест не менялся (A7).
- Тест проверяет поведение, а не реализацию.
- Покрыт путь отказа — ошибка, видимая наружу (то, что требует `rules.specs`).
- UI-изменение без зелёного headless-e2e (web — Playwright) — CRITICAL.

## Pass E: Безопасность
- Пользовательский ввод валидируется.
- SQL — параметризованные запросы, без конкатенации строк.
- Авторизация: проверка прав пользователя / изоляция тенанта.
- Нет утечек чувствительных данных в логи и ответы.
- Нет прямых ссылок на объект без проверки владения.

## Pass F: Полнота и границы
- `tasks.md`: каждый отмеченный чекбокс подтверждается кодом. **Отмеченная, но не сделанная
  задача — CRITICAL**: после archive проверить это будет уже не по чему.
- Незакрытые задачи явно перечислены — change не готов к архивации.
- Обновлены: схема API, публичная документация, счётчики/кодогенерат (если канон требует —
  и `git diff --exit-code` после перегенерации чист).
- Миграции имеют down-скрипт.
- Ошибки — через стандартный пакет ошибок проекта.
- Не сделано то, что `rules.tasks` прямо запрещает внутри change (бамп версии, публикация,
  теги, деплой — это отдельный шаг с ручным подтверждением).

## Pass G: Гейты и CI-готовность
- Команда-гейт из `rules.tasks` прогнана целиком и зелёная — приложить вывод.
- `openspec validate --all --strict` — зелёный. Помнить: он проверяет **только структуру
  markdown**, ничего не собирает и не тестирует; зелёный валидатор не является допуском к archive.
- CI-джоба спек-валидации не разъедется с локальной установкой: версия CLI в workflow
  запинена (`@fission-ai/openspec@<version>`), а не `@latest`.
- Ветка/коммиты соответствуют конвенции проекта; ничего лишнего не закоммичено.
